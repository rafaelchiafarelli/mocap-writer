What surrounds a change

The program runs and is tested in one Docker image. Every change travels a fixed branch chain and carries its as-built docs in the same commit. Bugs are written down and fixed when they get in the way.

A checklist for reviewing a change

  1. Does the commit do what its task file's contract says, and nothing outside it?
  2. Is the task file marked done in the same commit?
  3. Does the full suite pass in the image (docker/test.sh), not only the new tests?
  4. Do the new tests cover the contract's listed tests? For a dialog, does tests/CLAUDE.md say it was checked in the real window?
  5. Did every touched folder's CLAUDE.md and every changed stage in trelby.process.md change too? Do the file:line references still land on what they name?
  6. A new dependency: is it in the hashed lock, is its licence one that allows commercial use, and is it written down in docker/CLAUDE.md?
  7. A new file format or field: is it a mocap-contracts change at a new tag, never a private format?
  8. Film material (titles, scenes, characters of a real film) anywhere in the repository? It belongs in the film root.

Check yourself

The suite is green but a dialog crashes when opened. How could that happen?
The tests import a mock instead of wx, so no dialog is ever built in the suite. That is why every dialog change is also checked in the real window.
You find a bug while working on a task that it does not block. What do you do?
Record it as a bug file in its own commit and go on with the task; it is fixed on a fixes/ branch when it gets in the way.
Why are hashed locks worth the extra step?
The image installs exactly the reviewed files: a package changed upstream under the same version would fail the hash instead of slipping in.
